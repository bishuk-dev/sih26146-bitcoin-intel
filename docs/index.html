START HERE

Before we write code, understand the machine.

The team is not building a “Bitcoin AI.” We are building a small investigation system that takes messy transaction + network records, turns them into connected entities, finds suspicious behaviour, and shows a human why an entity was ranked highly.

Rule for everyone: you do not need to learn the whole field. Learn enough theory to make your module correctly, then learn by implementing it.

02 · WHAT IS ACTUALLY UNDER THE HOOD?

The data changes shape five times.

Raw rowsA transaction is just a record: timestamp, TXID, wallets, amounts, fee, IP and ports.
Clean tablesM1 fixes missing values, types, duplicates and bad records.
GraphM2 turns records into nodes and edges so relationships become queryable.
Feature tableM2 measures behaviour: transaction count, degree, burstiness, IP reuse, counterparties, etc.
Model outputM3 turns those measurements into suspiciousness signals; M4 turns signals into ranked alerts.
03 · THE CORE IDEA

Three questions, three tools.

“Does this look suspicious?”XGBoost learns from our synthetic training labels.
“Does this look strange?”Isolation Forest gives an independent anomaly signal.
“What is connected to it?”The graph shows the transaction and network evidence around the entity.
04 · ML DECISION

Why the current plan is XGBoost first, Isolation Forest second

official team plan
PRIMARY
XGBoost

Supervised model. We can train it because our synthetic generator provides ground-truth labels. It is also the easiest route to SHAP explanations.

features → class probability
SECONDARY
Isolation Forest

Unsupervised check. It asks whether behaviour is unusual compared with the wider population. It does not prove wrongdoing.

features → anomaly score
SUPPORTING
Clustering + graph

Groups similar entities and gives investigators the surrounding structure needed to inspect the alert.

features / edges → context

Important: the synthetic label is allowed into XGBoost training, but never as a feature. For evaluation, create separate train / validation / test scenarios so the model is not simply memorising the generator.

COMMON MISTAKES

Watch these

Random = realistic?

No. Behaviour is the point. Random rows without relationships are useless for this project.

Labels are public?

No. Keep them in the evaluation data path, not in the ML feature set.

Huge data first?

No. Get 100 rows working, then 10k, then 100k.

WHAT YOU NEED TO UNDERSTAND

Learn the idea before the library.

  1. FeatureA measurable property such as degree, burstiness or transaction count.
  2. SampleOne entity / wallet row.
  3. ClassificationLearn from labelled examples: benign vs anomalous.
  4. OverfittingModel memorises the training examples instead of learning a useful pattern.
  5. LeakageInformation from the answer sneaks into the features or test process.
  6. Precision / recall / F1Measure whether alerts are useful, not merely numerous.

YOUR BUILD ORDER

Follow this order

01
Build a toy classifier

Create 100–500 synthetic feature rows and train XGBoost on two classes. Do this before touching the Bitcoin pipeline.

X → XGBoost → probability → prediction
02
Create the feature list

Agree with M2 on the numerical feature columns. Example: transaction_count, total_inflow, counterparties, burstiness, degree, pagerank, IP_count.

03
Make three dataset versions

Training, validation and test must come from different random seeds and preferably different behaviour ranges. This is how you defend yourself against the “you trained on your own generator” question.

04
Train XGBoost

Start with a small CPU-friendly model. Save the feature list and the trained model. Do not tune ten parameters at once.

model.fit(X_train, y_train)
prob = model.predict_proba(X_test)[:, 1]
05
Measure the model

Report precision, recall, F1 and PR-AUC. Also record false positives. If the model catches every anomaly by flagging everything, that is not a success.

06
Add SHAP

Once the model is stable, use TreeExplainer to show the top features pushing a prediction higher or lower.

explainer = shap.TreeExplainer(model)
values = explainer.shap_values(X_one)
07
Add Isolation Forest

Train it on the same behavioural features without labels. Store its anomaly score separately. Do not pretend the score is a probability of crime.

08
Hand both signals to M4

Return class probability, anomaly score, cluster ID and top explanation features.

EVALUATION RULE

Ground truth is for training AND testing — but never as a feature.

X = df[FEATURE_COLUMNS]y = df["ground_truth_anomalous"]model.fit(X_train, y_train)metrics(y_test, predictions)

The test label is not shown to the model. It only lets us measure how well our detector did.

DO NOT CHEAT YOURSELF

Red flags in your own experiment

  • Random row split only.
  • Ground-truth column accidentally included in X.
  • Training and test generated with exactly the same tiny rule.
  • Accuracy shown without false positives.
  • “Confidence 97%” without saying what it means.

JUDGE QUESTIONS

Prepare short, honest answers.

Why XGBoost?

It is a strong CPU-friendly choice for our engineered tabular graph/temporal features and gives us a straightforward SHAP path.

Why also Isolation Forest?

It gives an independent unsupervised “how unusual is this?” signal.

Why synthetic data?

The PS requires synthetic data. We keep ground truth for evaluation and deliberately test on different generated distributions.

Does an alert prove crime?

No. It is an investigative lead based on behavioural and relational evidence.

Why a graph?

Because the useful question is often “what is connected to this entity?” rather than “what does this one row look like?”
